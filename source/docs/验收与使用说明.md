# 云朵宠物 · 验收与使用说明

本说明将业务引擎测试、浏览器交互检查和真实手机验收分别记录。任何一项不能替代另外两项。

## 访问状态

| 项目 | 当前事实 |
| --- | --- |
| 本地启动方式 | 项目目录执行 `node server.mjs`，默认端口 4173 |
| 局域网入口 | 启动日志或 `/api/network` 返回实际地址；电脑与手机须互通 |
| 公网入口 | [打开云朵宠物 H5](https://cr2262734404-cmyk.github.io/cloud-pet-demo/) |

| 静态三端联动 | 同一浏览器 localStorage；不同设备各自独立 |
| Node 三端联动 | 同一 Node 服务下共享 JSON 数据，可供多手机共同操作 |
| Android 真机 | 未执行：当前没有可控制的真实设备 |
| iPhone 真机 | 未执行：当前没有可控制的真实设备 |

二维码只有在内容确实指向当前可达地址时才是有效入口。公网 QR 必须使用最终 HTTPS 地址，局域网 QR 则需对应当前电脑 IP。不得将链接文本、二维码图片或电脑视口截图认作真实手机访问已经完成。

当前发布提交、GitHub Pages运行结果、逐文件HTTP与内容核验以 public-deployment-validation.json 为准。没有将公网可达性等同真实硬件验收。

## 测试准备

1. 使用演示数据；若此前修改较多，在老板端演示面板重置当前门店。
2. 记录使用的是局域网共享模式还是静态本地模式。两种模式的数据不能混合判断。
3. 记录设备型号、系统、浏览器版本、测试日期、网络条件。
4. Android 优先在实际 Chrome 中检查，iPhone 优先在实际 Safari 中检查；也可另测微信内置浏览器，但应单列结果。
5. 将失败的具体页面、操作步骤、预期与实际现象记下来。未测试的项目保留待验收。

## 十二条核心业务路径

| 场景 | 操作步骤 | 可观察结果 | 证据要求 |
| --- | --- | --- | --- |
| 顾客预约 | 顾客首页→服务→选宠物→选时间→确认提交 | 成功页有真实生成的演示 ID；老板排期出现对应预约 | 页面截图及预约 ID |
| 员工履约 | 老板确认/分配→员工任务→到店→开始→完成 | 一次收尾生成报告及待确认消费；顾客可看到报告 | 同一预约在三端的记录 |
| 机会归因 | 机会详情→联系→7 天内关联预约→完成服务→确认金额 | 预估、预约、实际与归因分开；实际金额确认后才计归因 | 机会 ID、预约 ID、消费 ID |
| 半自动提醒 | 查看话术→修改→人工联系标记或模拟授权渠道 | 日志标注人工/模拟结果，不声称实际发送 | 日志与文本 |
| 自动提醒 | 设置 auto+授权渠道+规则时间→执行检查 | 合格对象写模拟日志；无授权/冷却/暂停/免打扰被跳过 | 成功与跳过原因各一条 |
| 宠物礼物 | 员工报告→选主题→预览→两项质检→确认 | 未确认礼物不对顾客展示；确认后可查看/保存 | 员工预览与顾客结果 |
| 营销海报 | 选场景→改店名/文案/服务/宠物照片→预览→保存 | 预览随内容变化，导出图不截字、不变成其他宠物 | 导出的实际图片 |
| 空档补位 | 老板排期选择合适空档→代客预约 | 相应员工连续时段被占用；冲突提交被拒绝 | 前后排期及冲突提示 |
| 敏感与频控 | 测试退订、冷却、已离世宠物、刚联系过客户 | 不产生不合格触达；原因清楚；冷却后仅健在宠物恢复 | 拦截原因 |
| 角色与门店 | 顾客/员工/老板切换，再切另一门店 | 顾客仅自己的记录；员工仅分配范围、无财务汇总；门店隔离 | 至少一项越权拒绝及隔离对照 |
| 主题切换 | 春夏秋冬×四时段，手动和自动模式 | 界面变量与文案同步；图片不拉伸；导航与文字可读 | 16 张独立资源的实际页面截图与日月/宠物活动核对 |
| 异常状态 | 空数据、满档、生成失败、缺授权、漏填、断连 | 有原因与可恢复路径，原数据不出现部分写入 | 每类至少一条观察记录 |

有些种子机会已经完成或已预约，不能重复当作待联系任务。完整归因可从 `o2` 等可跟进机会开始。静态版必须在同一浏览器依次切换角色才能看到同一笔操作；跨手机共同演示请使用 Node 局域网版。

## 营业时间与容量验证

老板「门店设置」可修改每天统一的营业时间，例如 `10:30–20:00`。起止均须为半小时整点且结束晚于开始，支持结束 `24:00`；不支持跨天营业或一周不同日期的复杂班表。

保存后，顾客和老板时段视图读取同一 `openingHours`，服务必须在关闭前完成。例如 90 分钟项目在 20:00 关门时，18:30 可以开始，19:00 不可以。已存在预约不会因设置变更被自动删除或静默改时；需要门店按实际情况处理已有承诺。

## 真机通用检查

- 每类设备都应打开三端并完成至少一条预约与服务流程。
- 检查常见中文长名字、较长备注、键盘弹出、日期/时间选择和照片选择。
- 检查顶部安全区、底部导航、弹层关闭、返回、滚动与固定区域，不应挡住最后一项主要操作。
- 连续切换主题，检查插画完整度、文字对比度、玻璃层透明度及明显卡顿；可打开轻量模式对照。
- 报告、礼物与海报实际导出后检查分辨率、换行和内容。iPhone 可长按预览图保存；系统分享依浏览器能力而定。
- 若遇问题，在「手机自检与验收记录」选择发现问题并填写步骤，不要为了完成表单勾选未测试内容。

测试记录标记为 `self-report`、`validated:false`，表示测试者自行报告，系统没有独立识别硬件或认证报告真伪。顾客/员工能看本角色提交，老板能看本店所有记录；重置业务示例保留设备记录。

## 已有证据与未覆盖范围

自动化命令为 `node --test test-engine.mjs`。截至本说明更新，39 项通过，覆盖：角色与门店范围、预约时长/技能/物种/时间/动态营业时间、冲突和状态流、报告与消费生成、7 天归因、敏感状态和渠道规则、照片与存储错误、设备记录、持久化、HTTP 和静态相对路径构建。

这些核心测试不包含 Android/iPhone 真机操作、完整浏览器视觉、所有 Canvas 图片导出或公网访问验收。

另已在隔离桌面 Chrome 会话执行首页 16 个季节/时段状态 × 390×844、320×720、430×932 三种视口的 48 组截图与 DOM 几何检查。背景和图片均加载，未检出横向溢出或受检文字截断；首页预约按钮与底部导航命中正常，滚到页面底部后末操作未被固定导航覆盖。检查通过应用演示上下文设置主题，不能代替主题选择弹层的全部手动操作、全路由视觉验收或真机性能检查。记录见 `theme-validation.json`，截图见上级 `outputs/screenshots/themes`。

修复记录：静态打包曾误改图片路径规范化的前缀判断，造成图片变成 `../assets/` 并 404；现构建仅改具体文件 URL，保留前缀处理，并加入绝对/相对两种路径的回归断言。新版48组主题截图取自独立时段素材与刷新后的构建。

静态数据一致性修复已复验（`storage-validation.json`）：原问题是弹层期间忽略其他标签的存储通知，后续提交用旧数据覆盖新修改。当前每次写入前重读存储，并在支持 Web Locks 的浏览器中串行操作。隔离 Chrome 下重跑相同复现路径，外部宠物修改保留；另用主页面与同源 iframe 两个独立应用上下文并发保存主人/宠物资料，两项修改均保留。后者为真实独立引擎上下文测试，尚不是两台设备同步测试。无 Web Locks 的旧浏览器仍会写前重读，但没有经过同时写入的原子性验证。

`coverage-matrix.csv` 当前按入口、实现、引擎证据、浏览器与两类真机分别列出。完成真实检查后再更新对应列，并留下可复核证据。

## 当前需要明确保留的限制

1. 公网 URL 已完成发布和HTTP内容核验；用户手机网络下的实际访问及体验仍待真机验证。
2. 当前未执行 Android/iPhone 真实设备测试；不安排用户中途检查，也不以模拟器冒充通过。
3. 四季采用4张保留母图和12张独立时段延展；冬季清晨与白天的月亮星空已移除。
4. 机会任务是可解释的演示预置与实际动作联动，不是生产级持续机会扫描系统。
5. 微信消息、短信、支付、AI 头像生成、正式员工认证及真实多租户后端均未接入。
